# Research: Withdrawals and payout accounts (spec 013)

The engineering choices behind the plan, each written as **Decision / Rationale / Alternatives**. The product decisions are in the spec's Clarifications (Session 2026-10-03).

## R1 — Where the endpoints live

**Decision**: the surfaces specs 009–012 set up, not the Technical Spec's bare paths.

| Technical Spec | Built as |
|---|---|
| `POST /me/payout-accounts` | `POST /customer/me/payout-accounts` (trade gate) |
| — (clarification: several accounts) | `GET /customer/me/payout-accounts` (verified) · `POST /customer/me/payout-accounts/{account}/use|remove|keep` (trade) |
| — (email second-check, Part 1 §2.4) | `POST /customer/me/withdrawals/confirmations` · `GET /customer/me/withdrawals/confirmations/{confirmation}` (verified) · public `POST /withdrawal-confirmations/read` and `/confirm` (no token) |
| `POST /me/withdrawals` | `POST /customer/me/withdrawals` (verified) |
| `POST /me/withdrawals/{id}/cancel` | `POST /customer/me/withdrawals/{withdrawal}/cancel` (verified) |
| — | `GET /customer/me/withdrawals`, `GET /customer/me/withdrawals/{withdrawal}` (verified) |
| `GET /admin/withdrawals` | `GET /dashboard/withdrawals` · `/export` · `/{withdrawal}` |
| `POST /admin/withdrawals/{id}/review|release|reject` | `POST /dashboard/withdrawals/{withdrawal}/review|hold|unhold|release|reject` |
| `POST /admin/payout-accounts/{id}/verify` | `GET /dashboard/payout-accounts` · `POST /dashboard/payout-accounts/{account}/verify|refuse` |

**Rationale**: every customer write sits under `/customer/me/*` and every staff write under `/dashboard/*`. The confirm call is the one deliberate exception: it is opened from an email link on any device, possibly signed out (R5).

## R2 — No new database scope

**Decision**: every customer action here touches only the caller's own rows (their accounts, their withdrawals, their pauses, their wallet), so they run in the plain `customer` scope; the money service pushes `ledger` itself. Staff run in `staff`; the job in `system` (audited elevation); the public confirm in `bootstrap` (as the unauthenticated auth routes, `db.elevate:bootstrap`), touching only the confirmation row the token hashes to.

**Rationale**: no cross-customer read or write exists, so unlike specs 011–012 there is no Constitution II deviation.

**Alternatives considered**: a dedicated `confirmation` scope for the public call. Rejected: the bootstrap elevation already exists for exactly this shape (an unauthenticated call that must find one customer row by a secret), and the Action reads one row by its token hash.

## R3 — Schema, from the docs (Constitution III)

**Decision**: one migration, `2026_10_06_000010_create_withdrawals.php`, from `04_schema_market.sql` §12, with the docs updated first:

- **`payout_account_state`** gains `refused` (Clarification).
- **`payout_account`** as in the schema, plus:
  - `is_in_use BOOLEAN NOT NULL DEFAULT false`; partial unique index one per customer; CHECK `is_in_use → state IN ('active','removing')`.
  - `refusal_reason TEXT` (CHECK in the list), `refusal_note TEXT`; `name_checked_by/at` record the verifier **or** the refuser; CHECK `state = 'refused' ⇔ refusal_reason IS NOT NULL`.
  - `removal_requested_at`, `removed_at`.
  - `account_number_or_iban` CHECK: `^EG[0-9]{27}$` or `^[0-9]{8,20}$` (the IBAN checksum is checked in the request; the CHECK is the shape backstop).
  - `bank_name` CHECK length 2–80.
- **New `payout_account_change`** (the *Recent changes* list and Principle I history): customer, account, `kind` (`added`, `verified`, `refused`, `in_use`, `removal_scheduled`, `kept`, `removed`, `request_cancelled`), actor (customer / staff, CHECK exactly one), `pause_id`, created at. Append-only.
- **`withdrawal_pause`** as in the schema, plus `ended_notified_at TIMESTAMPTZ`.
- **`withdrawal`** as in the schema, plus:
  - `withdrawal_no BIGINT GENERATED BY DEFAULT AS IDENTITY UNIQUE` — shown as `WD-{n}` (the `TOP-{n}` precedent of spec 009; the staff and customer lists, the ledger history `reference` and the suggested transfer reference).
  - `hold_txn_id`, `return_txn_id` beside the existing `release_txn_id`; each UNIQUE.
  - review: `reviewed_by` (exists), `review_started_at`.
  - hold flag: `held_at`, `held_by`, `hold_reason` (CHECK list), `hold_message`, `hold_note`; CHECK all null or reason/message/by/at set.
  - rejection: `rejection_reason` (CHECK list), `rejection_note`.
  - release record: `bank_txn_number`, `transfer_reference`, `value_date DATE`; CHECK `state = 'released' → bank_txn_number IS NOT NULL AND release_txn_id IS NOT NULL`.
  - `ended_at` (released, rejected or cancelled), `cancelled_by_change BOOLEAN` (an account change, vs the customer's own cancel).
  - partial index `(state, requested_at)` for the queue.
- **New `withdrawal_confirmation`** (R5): customer, payout account, amount, `token_hash` UNIQUE, `expires_at`, `confirmed_at`, `used_at`, `replaced_at`, `withdrawal_id`, created at; partial unique index: one open (not used, not replaced) confirmation per customer.
- **`withdrawal_transition`** as in the schema, plus `requested → rejected` and `requested → cancelled` (the schema has `requested → cancelled`; adds `requested → rejected`). `on_hold_account_change` rows stay but are never reached.
- **New `payout_account_transition`** table with the FR-006 moves, and a guard trigger.
- **Guards**: `trg_withdrawal_guard` (BEFORE UPDATE: the move is in the table, identity/amount/account/customer never change, the txn ids are set once) raises SQLSTATE **`DH007`** → `illegal_withdrawal_transition`; `trg_payout_account_guard` raises **`DH008`** → `illegal_payout_account_transition` and freezes customer, bank, holder and number (a change is a new account).
- **Deferred money check `trg_withdrawal_money`** (AFTER INSERT OR UPDATE OF state, DEFERRABLE INITIALLY DEFERRED, reading under its own `ledger`-capable scope): `requested`/`under_review` → `hold_txn_id` set; `released` → `release_txn_id` set; `rejected`/`cancelled` → `return_txn_id` set and no `release_txn_id`.
- **Ledger**: `ledger_transaction.withdrawal_id` gets its FK (`lt_withdrawal_fk`, DEFERRABLE INITIALLY DEFERRED — the hold is posted before the withdrawal row exists, as spec 011's request FK).
- **RLS**: forced on `payout_account`, `payout_account_change`, `withdrawal_pause`, `withdrawal`, `withdrawal_confirmation` with `dahab_rls_elevated() OR customer_id = dahab_current_customer_id()` (the planned predicates in `05_schema_security.sql`).
- **Legal document** `payout_account_declaration` v1 (EN/AR from the terms draft), seeded in the migration as spec 011 seeded `deposit_agreement`.
- **Reversal**: `down()` refuses once any withdrawal exists (append-only ledger ties) and drops in reverse otherwise.

## R4 — Ledger lines

**Decision**: three shapes, all `event_kind = withdrawal`, tied by `withdrawal_id`, through `PostLedgerEntryAction` inside the caller's transaction:

```
hold     customer cust_available  −X    customer cust_held  +X     actor: the customer
release  customer cust_held       −X    bank               +X     actor: the releasing staff
return   customer cust_held       −X    customer cust_available +X actor: customer (cancel / account change) or staff (reject)
```

The bank's cash is `−SUM(bank)` (spec 008 R15), so a release lowers the cash figure by X. `insufficient_funds` from the money service carries `{ available, shortfall }` (the spec 011/012 `details` convention).

**Rationale**: the schema has one kind for "customer withdraws to bank"; the lines tell the three apart, and the withdrawal row names each txn (`hold_txn_id`, `release_txn_id`, `return_txn_id`) under unique constraints, so each happens at most once.

**Alternatives considered**: the return as a `reversal` of the hold through `ReverseLedgerEntryAction`. Rejected: a cancel or rejection is a business outcome, not a correction of an error; `reversal` is for mistakes (spec 008).

## R5 — The email second-check

**Decision**:

- `POST /customer/me/withdrawals/confirmations {amount, payout_account_id}` checks the FR-009 gates except the confirmation (no pause, account active/own/in use, funds), marks any open confirmation `replaced_at`, creates one with `expires_at = now + config('dahab-withdrawals.confirmation_ttl_minutes')` (30), a 32-byte random token (base64url) of which only `hash_hmac('sha256', token, app.key)` is stored, and emails (mail only, queued after commit) a link `config('dahab-withdrawals.confirm_url')` + `?token=…` — the Customer App route `#/withdraw-confirm`. Answer `201 { id, state: "sent", amount, payout_account, expires_at, email_masked }`.
- `POST /withdrawal-confirmations/read {token}` (public, throttled) → `{ state, amount, account_masked, expires_at }`, no side effect, so a mail scanner fetching the page changes nothing.
- `POST /withdrawal-confirmations/confirm {token}` (public, throttled, `db.elevate:bootstrap`) → sets `confirmed_at` when sent and unexpired; unknown/expired/replaced/used → `422 confirmation_invalid` (a new code; Part 1 §9 has none for the link page). Audited `withdrawal.email_confirmed` (actor = the customer).
- `GET /customer/me/withdrawals/confirmations/{id}` → the state (`sent`, `confirmed`, `used`, `expired`, `replaced`) for the app's *Waiting → Confirmed*.
- `POST /customer/me/withdrawals {confirmation_id, amount, payout_account_id}`: the confirmation must be the caller's, `confirmed`, unused, unexpired at submit, and match amount and account; otherwise `403 email_confirmation_required`. It is marked `used_at` and linked to the withdrawal in the same transaction.

**Rationale**: Part 1 §2.1/§2.4 (single use, short TTL, independent of the session: a stolen session cannot read the email); the prototype's *Waiting → Confirmed → Withdraw*; the Part 2 body keeps a confirmation reference (`confirmation_id` replaces `email_confirmation_token`, which the app never sees).

**Alternatives considered**: the `one_time_token` table with a new purpose. Rejected: it has no `confirmed_at`, amount or account, its purpose CHECK would need widening, and the confirmation needs its own forced RLS row and partial unique index. A link that confirms on GET. Rejected: mail scanners would confirm it.

## R6 — Account changes, the pause and cancellations

**Decision**: one concern, `ChangesPayoutAccounts`, used by the customer Actions and by verification.

- **Lock order**: the customer's `payout_account` rows (`ORDER BY payout_account_id FOR UPDATE`), then the customer's un-released `withdrawal` rows (`ORDER BY withdrawal_id FOR UPDATE`), then the money service's account locks. So every path takes accounts → withdrawals → ledger accounts.
- **Paths that start from a withdrawal id** (customer cancel, take for review, hold, unhold, release, reject): (1) read the withdrawal's `customer_id` **without a lock** (it never changes — the guard freezes it); (2) lock that customer's payout accounts as above; (3) lock the withdrawal row; (4) **re-check its state under the lock** and refuse with `illegal_withdrawal_transition` if it moved meanwhile. No path locks a withdrawal before the accounts, so there is no lock cycle with an account change.
- **`MakeAccountInUse`** (customer *use*, or verification when none is in use): clear the old in-use flag, set the new, write a `payout_account_change(in_use)`. If the customer has any earlier `in_use` change (ever), then: cancel each `requested`/`under_review` withdrawal (return entry, `cancelled_by_change = true`), and, when the setting is > 0, insert `withdrawal_pause(pause_until = now + hours)` linked from the change. Audit `payout_account.in_use_changed` (pause end, cancelled withdrawal numbers). Notify after commit.
- **Remove**: `pending_review → removed` (`request_cancelled`); `active` with un-released withdrawals → `removing` (`removal_scheduled`; **the in-use flag is kept** — the CHECK allows `removing` — so no other account silently becomes the one in use), else `removed` (in use cleared). `keep`: `removing → active` (no pause: nothing changed).
- **Using a `removing` account**: a new confirmation or submission requires the account in use to be `active` → `payout_account_not_active`. A **release** accepts `active` or `removing` (the money goes where the customer asked when they submitted).
- **Finishing a removal**: release, reject and cancel call `FinishesRemoval` in the same transaction: a `removing` account with no other un-released withdrawal becomes `removed` and loses its in-use flag (actor = the one ending the withdrawal; for staff, the history row names the staff member).
- **Making another account the one in use while one is `removing`**: the `removing` account loses its in-use flag (it stays `removing` until its withdrawals end — which the change itself ends, by cancelling them, so it becomes `removed` in the same operation).

**Pause semantics**: a request is refused while `EXISTS (pause WHERE customer AND pause_until > now())`. Release does not re-check the pause: every un-released withdrawal is cancelled at the change, so any withdrawal under review was requested after the latest pause ended (Part 2 §9's re-check is therefore moot; documented).

## R7 — Withdrawal Actions and lock order

- `RequestWithdrawalConfirmationAction`, `ConfirmWithdrawalAction` (public), `SubmitWithdrawalAction` (lock the confirmation, the customer's accounts, then post the hold through the money service — which locks and checks the wallet), `CancelWithdrawalAction` (customer), `TakeForReviewAction`, `HoldWithdrawalAction`, `UnholdWithdrawalAction`, `ReleaseWithdrawalAction`, `RejectWithdrawalAction` (staff), each one transaction, re-checking the state under the lock; `MovesWithdrawal` is the only code that changes `withdrawal.state` (sets `ended_at`, calls `FinishesRemoval`).
- Release checks the account is the customer's and `active` or `removing` (`payout_account_not_active` otherwise — e.g. it was refused or removed by staff action in a later feature).
- Races: release vs customer cancel vs account change all follow the R6 order (read the customer, lock the customer's payout accounts, lock the withdrawal, re-check): exactly one wins; the loser sees the new state and answers `illegal_withdrawal_transition`.

## R8 — Staff reads and the signals

- **`GET /dashboard/withdrawals`** (`withdrawal.release|wallet.view` to read; actions need `withdrawal.release`): keyset by `requested_at ASC, withdrawal_id` (oldest first); filters `state` (csv; default `requested,under_review`), `held=1`, `from`/`to` (Cairo dates), `q` (display ref, E.164 phone, name — the spec 007 search), `customer_id`. `meta.figures`: waiting (count, sum), released today (count, sum, Cairo day), on hold (count), average time to release (hours, last 30 days, `released_at − requested_at`).
- Item: number `WD-{n}`, customer ref + name, amount, the customer's available at read time, state, held flag + reason, requested at, review started / reviewer, account (bank, holder, number — full to `withdrawal.release`/`payout_account.verify`, masked otherwise), name check (by, at), `signals`.
- **Signals** (one query per page, no N+1): `identity_verified`, `suspended`, `account_added_at`, `account_verified_at`/`by`, `first_payout_to_account` (no released withdrawal to it), `payouts_to_account` (count), `in_use_changed_at` (the latest `in_use` change, when within 30 days), `completed_sales` (orders as seller in `ready_to_collect`/`completed`), `topped_up_never_traded` (a `topup` credit after the customer's last `deposit_hold`/`balance_payment`, or none ever).
- **Export**: CSV (UTF-8 BOM) of the filtered list, capped at 50,000 (`X-Export-Truncated`), audited `withdrawal.list_exported` — the spec 009 pattern.
- **`GET /dashboard/payout-accounts`** (`payout_account.verify`): `state` (default `pending_review`), oldest first, keyset; item: account (full number), customer ref, the customer's `full_name` (the verified ID name), identity verified, added at.

## R9 — The customer file and the wallet figures

- `CustomerFileResource` (`customer.view`) gains `payout_accounts[]` (masked number unless the caller holds `payout_account.verify` or `withdrawal.release`) and `withdrawal_pause` (`pause_until` or null). Withdrawals in the file come from `GET /dashboard/withdrawals?customer_id=` (`withdrawal.release|wallet.view`).
- The wallet figures gain `pending_withdrawals` and `held_on_orders` (`held − pending_withdrawals`), computed from the withdrawal rows in `requested`/`under_review` (their amounts equal their holds — reconciliation test): `GET /customer/me/wallet`, `GET /dashboard/customers/{id}/wallet`, `GET /dashboard/wallets/overview`. Additive optional fields (non-breaking).
- Ledger history `reference`: `WD-{n}` for `withdrawal` rows (as `TOP-{n}`).

## R10 — The job

`withdrawals:sweep`, every minute, `withoutOverlapping()`, system actor: select pauses with `pause_until <= now() AND ended_notified_at IS NULL`; per pause, in its own transaction, lock it, re-check; if a later pause of the same customer is still open, stamp without a message; otherwise stamp and notify `withdrawals_open` after commit. Audited `withdrawal.pause_ended` (system). 1,000 due pauses per run.

## R11 — Notifications

`PayoutNotification` with a `PayoutEvent` enum — `account_added`, `account_verified`, `account_refused` (reason), `account_in_use` (pause end, the cancelled numbers), `account_removed`, `withdrawal_held` (the staff's message), `withdrawal_released` (amount, account masked, value date), `withdrawal_rejected` (reason), `withdrawals_cancelled_by_change`, `withdrawals_open` — SMS plus email, queued, after commit, in the customer's language, following `OrderNotification`. `account_added` and `account_in_use` go even though the customer acted (Clarification and terms §9.3: "you are told on your current number and email" — a hijacked session must not change the account silently). `WithdrawalConfirmationMail`: mail only, the link, the amount and masked account, the 30-minute life.

## R13 — Permissions

`withdrawal.release` (*Release a withdrawal* — queue, review, hold, unhold, reject, release, export; seeded CEO, Finance; never COO) and `payout_account.verify` (*Verify a payout bank account*; CEO, Finance, Verification), group "Money" / "Customers", seeded once, editable from the Dashboard. Reading the list and a withdrawal also opens with `wallet.view` (a read of wallet figures, used by the Customer file): no action, no export, account numbers masked (spec FR-012).

Settings are read through an injected `App\Support\Pricing\Settings` instance — `$settings->integer(SettingKey::WITHDRAWAL_ACCOUNT_CHANGE_PAUSE_HOURS)` — never a static helper (analysis U1).

## R14 — Validation

- Amounts: `regex:/^\d{1,12}(\.\d{1,2})?$/`, `> 0` (the spec 009 rule); returned with 4 places.
- IBAN: strip spaces, upper-case; `EG` + 27 digits; ISO 13616 mod-97 = 1 (bcmath). Account number: 8–20 digits. Bank 2–80, holder 3–120 (trimmed). The declaration must be the current `payout_account_declaration` id and `accepted = true` (`declaration_required` 422 — the spec 010 pattern `ownership_declaration_required`).
- Staff: reasons from the enums; notes 3–1000; hold message 3–500; bank transaction number 3–64; transfer reference ≤ 64; value date not in the future, not before the request date.
- Rate limits: `customer.payout_accounts` (5/min), `customer.withdrawals` (10/min), `public.withdrawal_confirmations` (10/min per IP).

## R15 — Tests

Pest feature tests through HTTP on PostgreSQL (`dahab_wt013`, sequential, as `dahab`): schema (guards, CHECKs, deferred money check, RLS per scope), every endpoint and refusal, idempotent replay, the confirmation life (expiry with `travelTo`, replacement, reuse, another customer, amount mismatch, the public read has no side effect), the pause and its setting (48, changed, 0), the job by command, permissions (COO 403 + audit, Verification may verify but not release), isolation and column privacy (masked numbers; no other customer), the wallet split, concurrency on two connections with committed fixtures then truncate (release vs cancel, release vs account change, two submits over the balance, verify vs remove), and `WithdrawalReconciliationTest` over every withdrawal (one hold equal to the amount; exactly one release or return once final; held back to zero; `ledger_global_zero`). The build tests (`CustomerTableIsolationTest`, `CustomerRouteGateTest`, `PermissionCatalogueTest`, `ElevationTest`) pick the new tables, routes and codes up.

## R16 — Local seeder

`LocalWithdrawalSeeder` (local only, after `LocalOrderSeeder`) drives the real Actions: customers with an account under review, a refused one, a verified one in use, a second verified one, one `removing`; withdrawals `requested`, `under_review`, `under_review` held, `released` (bank details), `rejected`, `cancelled` by the customer and `cancelled` by an account change (with an open pause); an ended pause already announced.
